# Maintain the content changelog

Use the deterministic CLI from the repository root. It records one release version for the staged change set and one file entry for every changed content file.

```bash
.venv/bin/python skills/content-changelog/scripts/content_changelog.py update --staged --stage
.venv/bin/python skills/content-changelog/scripts/content_changelog.py validate --staged
.venv/bin/python skills/content-changelog/scripts/content_changelog.py validate --base origin/master
```

The canonical changelog is `content_release_notes.yaml`. Do not create a second changelog file.
When historical entries are intentionally pruned and the retained history is empty, the next generated patch version continues from `metadata.version`.

## Update staged changes

The `update --staged` command:

1. Reads only staged JSON changes under `navigators/`, `detector/`, and `group/`.
2. Creates one semantic patch version for the staged change set.
3. Adds one entry per added, modified, deleted, or renamed content file.
4. Extracts the content name and generates a concise description from the
   semantic staged JSON diff, using the previous committed object as its baseline.
5. Uses a stable change ID so retrying the same commit does not create duplicates.
6. Replaces only an uncommitted entry previously generated by this CLI when the staged content changes.
7. Stages `content_release_notes.yaml` when `--stage` is supplied.

After generation, improve descriptions, change types, notes, or breaking-change flags when the staged diff supports a more precise explanation. Preserve the generated `change_id`, `generated_by`, version, paths, and one-entry-per-file coverage. A subsequent run with the same staged content preserves those edits.

## Automatic pre-commit behavior

The repository hook runs Master SignalBuddy synchronization first so canonical exported JSON is staged before changelog generation. It then updates and validates the changelog. Any generation, parsing, staging, or coverage failure blocks the commit.

The pre-commit path is local and deterministic; it must not call an AI service or require network credentials. Generated descriptions identify actual changed fields while ignoring export-only metadata such as hashes and timestamps. `git commit --no-verify` remains the explicit emergency bypass.

## Validation

- `validate --staged` requires the exact staged content change ID and all staged content paths in the staged changelog.
- `validate --base <ref>` is for CI and requires every content path changed since the merge base to appear in a new changelog version added since that base.
- Historical mentions that were already present at the base do not satisfy coverage for a new change.

Do not silently pass when Git, YAML parsing, or base-ref resolution fails.
